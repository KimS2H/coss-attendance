## ① 강의실 코드 표시 (A1~A3)

- 총관리자가 "장소·일정"에서 수업의 "코드 띄우기"로 L-03 코드 화면을 열면 화면이 남은 시간을 1초씩 줄이다가 0이 되면 API에 새 코드를 요청한다.
- API는 코드를 **저장하지 않고 계산**한다: `수업 ID + 30초 구간 + 서버 비밀 값(APP_SECRET)`으로 4자리 숫자를 만든다. 서버만 비밀 값을 알기 때문에 학생은 미리 알 수 없다.
- 학생이 입력하는 사이에 코드가 바뀔 수 있으므로 **바로 전 30초 코드까지** 인정한다.

## ② 학생 출석 체크 (B1~B21)

### 출석 요청에 담기는 값 (B6)

| 값 | 설명 |
|---|---|
| 회차 ID | 지금 출석할 수업 |
| 좌표 · 정확도 | 브라우저 위치 기능 결과. 서버는 거리만 계산하고 좌표는 저장하지 않음. 위치 동의를 안 했거나 권한이 없으면 비워서 보냄 |
| 강의실 코드 | 학생이 입력한 4자리 |
| 기기 쿠키 `did` | 처음 접속한 브라우저에 서버가 준 임의 값(400일). 브라우저가 자동으로 보낸다. 서버에는 해시만 저장 (`devices.fingerprint_hash`) |

시각은 보내지 않는다. 모든 판정은 서버 시각 기준이다.

### 판정 순서 (B8~B10)

| 순서 | 판정 | 실패 시 결과 (`attendance_attempts.result`) | 학생 화면 메시지 |
|---|---|---|---|
| 0 | 로그인 세션 유효 (3시간) | — | 로그인 화면으로 |
| 0 | 수강 중인 회차인지 | `not_enrolled` (저장 안 함) | 이 수업의 수강 정보가 없어요 → 문의 |
| 0 | 이미 처리됐는지 | `already` (저장 안 함) | 현재 상태를 그대로 보여 줌 |
| ① | 출석 가능 시간 | `too_early` / `closed` | 아직 출석 시간이 아니에요 (09:55부터) / 수업이 끝났어요 |
| ② | 위치가 있는지, 거리 − min(정확도, 50m) ≤ 허용 반경(기본 50m) | `gps_denied` / `out_of_range` | 위치 권한을 켜 주세요 / 출석 장소에서 약 350m 떨어져 있어요 |
| ③ | 강의실 코드 (지금 또는 직전 30초 코드) | `code_wrong` | 강의실 코드가 맞지 않아요 |
| ④ | 같은 수업에서 이 기기로 다른 학생이 이미 출석했는지 | `proxy_canceled` (주인이 아닌 쪽, 출석 취소로 저장) | 출석이 취소되었어요 · 같은 기기로 다른 계정이 출석했어요 |
| ⑤ | 이 학생의 등록 기기인지 | `pending_device` (실패가 아니라 승인 대기) | 등록되지 않은 기기예요 · 승인 대기 |

- ①부터 차례로 확인하고, 하나라도 실패하면 그 사유로 응답한다. 실패해도 HTTP 응답은 정상(200)이고 `result`로 구분한다.
- 거리 판정에서 GPS 정확도를 최대 50m까지 빼 주는 이유: 실내에서는 GPS 오차가 커서, 강의실 안에 있어도 반경 밖으로 나오는 경우를 줄이기 위해서다.
- 위치 동의를 하지 않은 학생은 `gps_denied`가 된다. 이때 학생은 문의하고, 인솔자가 출결 변경을 신청해 총관리자 승인으로 처리한다.

### 출석 시간 규칙 (판정 ①과 출석·지각 구분)

| 서버 시각 | 결과 |
|---|---|
| 시작 5분 전 이전 | 출석 불가 (`too_early`) |
| 시작 5분 전 ~ 시작 5분 후 | 출석 (`present`) |
| 시작 5분 후 ~ 수업 종료 | 지각 (`late`) |
| 수업 종료 후 | 출석 불가 (`closed`). Worker가 결석(`absent`) 처리 |

### 결과별 저장 (B11~B21)

| 경우 | 저장 내용 | 학생 화면 |
|---|---|---|
| ①~③ 실패 (B11) | `attendance_attempts`만 기록 | 실패 사유 + 다시 시도 + 문의 링크 |
| ④ 같은 기기, 기기 주인 (B13) | 내 출석은 출석/지각 저장, 상대 계정 출석은 `canceled`로 바꿈. 두 출석 모두 `suspicious`, 상대 쪽 `attendance_changes`(처리자 system)·`penalties`(출석 취소)·대기 중이던 기기 승인 자동 거절. 담당 인솔자·총관리자에게 알림 | "출석" 또는 "지각" |
| ④ 같은 기기, 주인이 아닌 계정 (B13) | 내 출석을 `canceled`로 저장, `penalties`(출석 취소), 상대 출석에 `suspicious` 표시. 알림 | "출석이 취소되었어요" + 문의 링크 |
| ⑤ 등록 기기 (B16) | `attendances` 저장 (판정 시각 = 요청 시각) + 시도 기록 | "출석" 또는 "지각", 버튼 비활성화 |
| ⑤ 미등록 기기 (B18) | `devices`(pending), `attendances`(pending_device), `device_approvals`(pending), 시도 기록. 이 기기가 다른 학생의 등록 기기면 `suspicious`("다른 학생의 등록 기기"). 담당 인솔자에게 이메일 + 화면 알림 | "승인 대기" + 대리 출석 경고 문구 |

### 동시 요청·중복 방지 (B7, B10)

- 요청 횟수 제한: 학생당 1분에 10번 (Redis). 넘으면 "잠시 후 다시 시도".
- 같은 수업의 출석은 **DB 잠금**(PostgreSQL advisory lock, 수업 ID 기준)으로 한 번에 하나씩 처리한다. 두 계정이 같은 폰으로 동시에 눌러도 대리 출석 판정이 꼬이지 않는다.
- DB에도 `attendances (student_id, session_id)` 고유 조건이 있어 같은 학생·수업에 2건이 저장되지 않는다.

## ③ 미등록 기기 승인 (C1~C11)

- 인솔자는 메일이나 메뉴의 알림 배지를 보고 L-08 화면을 연다. 총관리자도 같은 처리를 할 수 있다.
- 목록에는 이 기기가 다른 학생의 등록 기기인지(기기 주인 이름)가 표시된다.
- **승인:** 판정 시각을 승인한 시각으로 정하고 출석 시간 규칙을 적용한다.
  - 시작 5분 후 이내면 출석, 수업 종료 전이면 지각, 종료 후면 결석.
  - 같은 트랜잭션에서 새 기기를 `active`로, 이전 기기를 `retired`로 바꾸고 이력을 남긴다.
  - 단, 이 기기가 **다른 학생의 등록 기기**이면 출석만 인정하고 기기는 등록하지 않는다.
- **거절:** 사유를 적고, 승인 요청과 기기를 `rejected`로 바꾸고, 출석은 결석으로 처리한다.
- 학생 화면은 30초마다 자동으로 새로 읽어서 결과가 바뀐다.
- 사정이 있으면 인솔자가 출결 변경을 신청하고, 총관리자가 승인하면 바뀐다.

## 그림에 없는 관련 흐름

### 첫 로그인과 기기 등록

- 학생이 처음 로그인하면 그 브라우저를 등록 기기로 정한다 (`newly_registered`).
- 단, 그 브라우저가 이미 **다른 학생의 등록 기기**이면 등록하지 않는다 (`unregistered`). 남의 폰으로 처음 로그인해도 그 폰이 내 기기가 되지 않는다.
- 폰을 바꾸거나 잃어버리면 인솔자가 "기기 초기화"를 하고, 다음에 로그인한 기기가 새로 등록된다.

### 자동 결석

수업이 끝나면 Worker(1분마다)가 수강생 중 `attendances` 행이 없는 학생을 결석으로 만든다 (오늘·어제 수업). 승인 대기(`pending_device`) 상태로 남은 건은 그대로 두고 인솔자 처리를 기다린다.

### 문의·오류 신고

1. 학생이 모든 화면 상단의 "문의" 버튼으로 분류를 골라 문의한다. 기기 정보와 마지막 출석 시도 결과가 자동으로 붙는다 (`tickets`, 좌표 제외).
2. 같은 학교 인솔자에게 화면 알림과 이메일이 간다.
3. 인솔자가 답변하고 해결 처리한다. 해결이 어려우면 총관리자에게 넘긴다(`status = escalated`).
4. 출석 인정이 필요하면 인솔자가 문의와 연결해 출결 변경을 신청한다 (아래).
5. 인솔자 본인의 문제는 처음부터 총관리자에게 신고한다.
6. 학생 문의를 포함한 모든 문의 기록은 총관리자가 볼 수 있다.

### 출결 변경 신청·승인

1. 인솔자가 학생·수업, 변경 후 상태, 사유를 적어 신청한다 (`attendance_change_requests`, `pending`). 미출이면 결석 행을 먼저 만든다. 같은 출석에 처리 중인 신청은 1건만 가능하다.
2. 총관리자에게 이메일과 대시보드 알림이 간다.
3. 총관리자가 승인하면 `attendances.status`를 바꾸고 `attendance_changes`에 이력을 남긴다. 인솔자에게 결과를 알린다.
4. 미승인이면 사유와 함께 인솔자에게 돌려준다.
5. **10분 안에 총관리자가 답하지 않으면 우선 거절한다** (`auto_rejected`, Worker가 1분마다 확인). 출석은 그대로 두고, 인솔자에게 "우선 거절, 총관리자가 나중에 다시 확인"을 알린다. 인솔자는 다시 신청하지 않아도 된다.
6. 우선 거절된 신청은 총관리자의 "재검토 대기"에 남는다. 나중에 승인하면 그때 반영하고, 거절을 확정하면 사유를 적는다. (24시간 재알림은 운영 시작 후 추가 예정)

### 대리 출석 처리

- **취소 대상: 같은 수업에서 같은 기기로 출석한 두 계정 중 기기 주인이 아닌 계정.** 시스템이 바로 출석 취소(`canceled`, 결석으로 집계)하고, 두 출석 모두 `suspicious`로 표시한다.
- **기기 주인은 순서와 관계없이 유지한다.** 다른 학생이 주인 기기로 먼저 출석해 승인 대기 중이어도, 주인이 출석하는 순간 그 학생의 출석이 취소로 바뀐다.
- 둘 다 주인이 아니면(제3자의 기기) 두 번째로 출석한 계정을 취소한다. 먼저 출석한 쪽이 아직 승인 대기여도 "이미 출석한 행"으로 본다.
- 주인이 그 수업에 출석하지 않으면 다른 학생 한 명만 그 기기를 쓴 것이므로 자동 취소하지 않는다. 기기 승인 대기로 두고, 인솔자 화면에 "다른 학생의 등록 기기"로 표시해 인솔자가 판단한다.
- 미등록 기기 학생 화면의 경고 문구: "대리 출석의 경우 벌점, 수료 불가, 출석 취소 등 불이익이 있습니다. 같은 기기로 두 계정이 출석하면 기기 주인이 아닌 계정의 출석이 취소됩니다."
- **불이익:** 출석 취소는 자동으로 `penalties`에 남는다. 벌점과 수료 불가는 총관리자가 대리 출석·불이익 화면(A-11, 운영 시작 후 추가 예정)에서 사유와 함께 정한다. 벌점 점수와 수료 불가 기준은 사업 규정을 따른다.
- 정당한 사유가 있으면(예: 휴대폰 고장으로 친구 기기를 빌림) 학생이 문의하고, 인솔자가 출결 변경을 신청해 총관리자 승인을 받는다.
- 한계: 시크릿 창이나 다른 브라우저를 쓰면 기기 쿠키가 달라져 같은 기기로 알아채지 못한다. 대신 "미등록 기기"가 되어 인솔자 승인을 거쳐야 하므로 그냥 통과되지는 않는다.
